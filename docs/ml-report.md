# Foresight · ML: модели, валидация, инференс

Отчёт ML-блока. Сабмиты записаны в [`submissions.md`](submissions.md), контракт библиотеки описан в
[`api-contract.md`](api-contract.md) §4. MAE везде в секундах. Все цифры получены на сервере `home-wsl`
(RTX 3060, i5-12400F); сырой отчёт обучения v2 лежит в `/root/mt-hackathon/artifacts/v2_train/report.json`.

## 1. Постановка и протокол валидации

Для точки `(tr_id, T)` модель предсказывает задержку на целевой остановке, плановое прибытие которой лежит в
`(T+10, T+15]` мин. Метрика — MAE.

- **Данные.** train — 4 434 точки (39 ТС: 13 реальных, остальные — синтетические копии), test — 353, validate — 151.
- **Утечка через синтетику.** Синтетические копии покрывают и периоды test/validate. Из train исключаются
  1 985 строк копий, чей эквивалентный момент ближе 30 мин к точке оценки (`ml.dataset.leak_mask`), как в v1.
  Для обучения остаются 2 449 строк, из них 1 141 — реальные ТС.
- **CV.** GroupKFold(5) по семьям ТС (реальное ТС вместе с его копиями). Фолды общие для всех компонент.
  Метрика считается по реальным ТС.
- **Test — только holdout.** Модели для test обучены только на train. По test ничего не выбирается.
- **Выбор по OOF (реальные ТС).** На OOF выбираются вариант сети и число эпох (ранняя остановка), вес
  ансамбля, центр интервала и поправка CQR, калибровка `p_late` и способ оценки ожидаемой ошибки. Для веса
  ансамбля есть вложенная оценка: вес подбирается по OOF остальных фолдов. Она и записана в манифест как
  `cv_mae`.
- **Финальные модели** обучены на train + test.

## 2. Входы

- **54 табличных признака v1** (`shared/features.py`, без изменений): отклонение по детектору и его тренд,
  привязка GPS к плану, движение и простои, маршрут до цели, отстой на конечной, «физика», час, lead.
- **Последовательность телеметрии** (`shared/sequences.py`, новый модуль, общий для офлайна и потока). Окно —
  20 мин до `T`, сетка 15 с, итого 80 шагов × 12 каналов. Каналы:
  - маска пропуска GPS;
  - средняя скорость и доля точек стоянки;
  - смещение за шаг и возраст последней GPS-точки;
  - отклонение по последнему подтверждённому проходу детектора и его возраст;
  - расстояние до следующей плановой остановки, насколько её план уже прошёл, признак отстоя перед ней.

  Шаг `k` читает только GPS с `event_time ≤ t_k ≤ T`, проходы с `confirmed_at ≤ t_k` и плановое расписание.
  Контекст тот же, что у признаков (`FeatureContext`: телеметрия сплита, план без факта, проходы детектора).
  Последовательность не зависит от целевой остановки, поэтому на потоке её достаточно строить раз на ТС за тик.

## 3. Модели v2

| Компонента | Модель | Выход |
|---|---|---|
| Задержка, CatBoost | ансамбль v1: CatBoost MAE, 2 варианта × 2 сида (реальные ТС; остаток к `cur_dev_s` с синтетикой веса 0.5) | `pred_delay_s` (вес 0.55) |
| Задержка, GRU | `gru_reg_h64`: GRU(12→64) по последовательности + табличные признаки (робастная нормировка, маска NaN → 32) → голова 64 → остаток к `cur_dev_s`. | Опоздание | CatBoost Logloss `delay > 120 с` + стекинг-калибровка на OOF: `σ(a·logit p + c·(pred − 120)/100 + b)` | `p_late` |

## 5. Интервал P10–P90 и ожидаемая ошибка

- Сама модель MultiQuantile слишком узкая. На OOF её P10–P90 покрывает лишь 39% при ширине 85 с. Вероятная
  причина — почти одинаковые копии ТС в обучении: разброс внутри train меньше, чем между семьями ТС.
- CQR по OOF добавляет к обеим границам по **85.7 с**. Итог: покрытие OOF **80.1%** (при перекрёстной оценке
  80.3%), test **85.8%** (5.7% ниже P10, 8.5% выше P90). Средняя ширина — 256 с на OOF и 276 с на test.
- Проверен вариант, где поправка CQR масштабируется шириной интервала. При том же покрытии 79% интервал выходит
  шире (344 с), поэтому оставлен аддитивный вариант.
- Ширина интервала почти не отражает ошибку конкретной точки: Spearman между шириной и |ошибкой| на OOF 0.04.
  Поэтому `expected_abs_error_s` считает отдельная модель. Выбор между шириной и моделью — по OOF Spearman.

| `expected_abs_error_s` | Spearman с \|ошибкой\|, OOF | Spearman, test | Среднее, test (факт 75.6) |
|---|---|---|---|
| k · (p90 − p10) | 0.04 | 0.18 | 81.8 |
| **CatBoost по OOF-ошибкам** | **0.18** | **0.28** | 77.0 |

Если разбить точки test на терцили по ожидаемой ошибке, средние ожидаемые значения — 61 / 75 / 94 с, а
фактические — 61 / 77 / 89 с.

## 7. ONNX и INT8

Три сида GRU собраны в один граф (`SeedEnsemble`). Вход графа — `seq (B, 80, 12)` и `tab (B, 54)` с NaN,
выход — остаток задержки. Нормировка признаков встроена в граф. Экспорт делает `torch.onnx.export` (opset 17).
Для квантования GRU развёрнут по шагам (`UnrolledGRU`): динамическое INT8-квантование ONNX Runtime не
обрабатывает оператор `GRU`, а после развёртки каждый шаг становится `MatMul`, и INT8 покрывает всю
рекуррентную часть. Модели обучены только на train, замеры — на test.

| Граф | Файл | Веса | max \|Δ\| с PyTorch | MAE test: GRU / ансамбль | ORT CPU, p50: батч 1 / 100 / 1000, мс |
|---|---|---|---|---|---|
| fp32, оператор `GRU` | 314 КБ | 297 КБ | 3.6·10⁻⁵ с | 78.22 / 75.64 | 0.32 / 12.7 / 122.0 |
| fp32, развёрнутый | 1.60 МБ | 297 КБ | 7.1·10⁻⁵ с | 78.22 / 75.64 | 3.35 / 16.1 / 123.9 |
| **INT8** dynamic (из развёрнутого) | 1.60 МБ | **80 КБ** | 2.49 с | 78.12 / **75.60** | 2.73 / **11.9** / **99.3** |

- INT8 уменьшает веса в 3.7 раза. MAE не меняется: разница в пределах шума, 0.04 с на ансамбле.
- На больших батчах INT8 быстрее в 1.23 раза: 99 мс против 122 мс на 1 000 строк. На батче 1 он медленнее
  fp32 с оператором `GRU`, потому что развёрнутый граф — это 80 шагов × 3 сида узлов. Файл INT8 больше fp32
  с `GRU` по той же причине.
- На validate прогноз v2 в INT8 и fp32 расходится максимум на 0.87 с, в среднем на 0.23 с.
- Версия по умолчанию загружает INT8. `load_bundle("v2", precision="fp32")` загружает `seq.fp32.onnx`.
  CUDA EP не используется, инференс идёт на CPU.

**Воспроизводимость.** Сиды python / numpy / torch плюс детерминированный cuDNN. Повторное обучение тех же
сидов на GPU расходится с прогнозом стадии CV не больше чем на 9.7·10⁻⁵ с. На CPU
`tests/test_inference_v2.py::test_train_net_reproducible_by_seed` сверяет прогнозы бит в бит.

## 9. Честность: что проверяется

- **Последовательности** (`tests/test_sequences.py`). На синтетическом маршруте и на реальных данных test
  (4 ТС, каждая 7-я точка) последовательность совпадает бит в бит в трёх случаях:
  - телеметрия обрезана по `T`, детектор пересчитан;
  - данные после `T` испорчены и дополнены лишними точками;
  - проходы после `T` сдвинуты (`pass_time`, `confirmed_at`), в расписание добавлены `time_fact_begin` и
    `manual_fill`.

  Дубликаты `(tr_id, T)` и неизвестные ТС тоже проверяются.
- **Признаки** — те же тесты для `shared/features.py`, как в v1 (`tests/test_features.py`).
- **Протокол.** Копии синтетики возле периодов test/validate исключены. Все решения приняты по OOF реальных ТС,
  test только отчётный. `cv_mae` в манифесте считается с вложенным весом.
- **Остаточный оптимизм CV.** Вариант сети и число эпох выбраны по тем же OOF, по которым считается CV. Вложенная
  оценка покрывает только вес ансамбля, поэтому CV 76.72 может быть оптимистичнее на десятые доли секунды.
- **Модель ожидаемой ошибки** обучена только на out-of-sample ошибках: OOF train и holdout test.
- **Защита от рассинхрона кода.** `load_bundle` не загрузит версию, если `features_version` или
  `sequence_version` манифеста не совпадают с текущим кодом признаков и последовательностей.

## 10. Что сработало и что нет

- ✅ Последовательность полезна поверх табличных признаков. GRU с признаками даёт CV 77.75 против 78.41 у MLP
  на тех же признаках.
- ✅ Ансамбль с CatBoost улучшает CV на 0.24 с (76.96 → 76.72, вложенный вес) и test на 0.19 с
  (75.79 → 75.60). Больше всего выигрыш на точках с отстоем: 83.0 → 81.1.
- ✅ Интервалы с поправкой CQR дают целевое покрытие. `p_late` после стекинга лучше базовой частоты на 19%
  на OOF и на 28% на test (по Brier).
- ❌ Без регуляризации сеть переобучается за 2–3 эпохи: к 80-й эпохе OOF MAE растёт с 78 до 89. Transformer
  хуже GRU.
- ❌ Выигрыш v2 по MAE мал, в пределах шума между фолдами: веса по фолдам 0.21–0.54. Точки без отстоя на test
  у ансамбля немного хуже, чем у одного CatBoost: 74.06 против 73.70.
- ❌ GRU только по последовательности даёт лучший вложенный CV ансамбля (76.53), но его test равен 91. Это
  неустойчиво, и по протоколу такой вариант остаётся абляцией.
- ❌ Ширина интервала почти не зависит от точки. Файл INT8 из-за развёртки не меньше fp32 с оператором `GRU`.
- ⚠️ Без последовательностей v2 считает задержку только CatBoost-частью: в среднем на 18.6 с иначе, чем полный
  ансамбль на test. Остальные выходы работают. Чтобы на потоке работал GRU, predictor должен передавать
  последовательность (§12).

## 11. Реестр версий и формат артефактов

Версия модели — это каталог `artifacts/models/<version>/`: `manifest.json` и файлы моделей. Каталог моделей
задаётся переменной `FORESIGHT_MODELS_DIR`, по умолчанию `artifacts/models` в корне репозитория. Общий каталог
на сервере — `/root/mt-hackathon/artifacts/models/`.

| Поле `manifest.json` | Смысл |
|---|---|
| `format` | `foresight-model/1` |
| `version`, `created_at` (UTC), `git_commit` | имя версии, момент обучения, коммит кода обучения |
| `features`, `features_version` | признаки в порядке модели; хэш кода признаков (`ml.dataset.code_version`) |
| `sequence_version` | хэш `shared/sequences.py` (у версий с `sequence`) |
| `components`, `precision`, `capabilities` | `["catboost"]` / `["catboost", "gru"]`; `fp32` / `int8`; подмножество `{quantiles, p_late, factors, sequence}` |
| `metrics` | `cv_mae` (GroupKFold по семьям ТС, реальные ТС; у v2 — с вложенным весом), `test_mae` (holdout), baseline, покрытие интервала, Brier / ECE `p_late`, `platform_score` |
| `ensemble` | `mean` (v1) или `weighted` с весами компонент (v2) |
| `members` | модели: файл, компонент (`catboost` / `gru` / `transformer`), цель (`delay` / `quantiles` / `p_late` / `abs_error`), база остатка; у `p_late` — `calibration` (`none` / `platt` / `isotonic` / `stack`); у GRU — `fp32_file`, `precision`, `sequence` (`len`, `step_s`, `channels`) |
| `intervals` | центр интервала, поправка CQR, `abs_error_k` (запасной способ ожидаемой ошибки) |
| `files` | SHA-256 и размер каждого файла; сверяются при загрузке |
| `latency_cpu` | замер `ml.registry bench` |

| Версия | Модель | Возможности | CV MAE | Test MAE | Размер | Score |
|---|---|---|---|---|---|---|
| `v1` | CatBoost MAE, 2 варианта × 2 сида, среднее; 54 признака | `factors` (остальные выходы = null) | 76.96 | 75.79 | 4.4 МБ | 0.87636 |
| `v2` | v1 + GRU INT8 (вес 0.45) + MultiQuantile / CQR + `p_late` (стекинг) + модель ожидаемой ошибки | `quantiles`, `p_late`, `factors`, `sequence` | 76.72 | 75.60 | 9.4 МБ | — |

## Дообучение на потоке

Кнопка «Переобучить на потоке» (`POST /api/admin/models/retrain` → ml-service `POST /model/retrain`, `ml/online.py`)
берёт последние 20 000 закрытых на потоке прогнозов активной версии (факт — детектор остановок) и подбирает поправку
`a + b · прогноз` медианной регрессией (как MAE модели) на ранних 70 %; MAE до и после меряется на поздних 30 %.
Снизила — поправка сохраняется новой версией `<база>-online<N>` (копия базы + `online_calibration` в манифесте;
P10/P50/P90 сдвигаются той же поправкой), иначе версия не создаётся. Новая версия не включается сама. Это
калибровка выхода, а не переобучение CatBoost/GRU: признаков в журнале нет. Демо-поток — тестовый день по кругу,
поэтому выигрыш на нём оптимистичен (поправка видела тот же день на прошлых кругах).
