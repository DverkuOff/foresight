## 0. Название

**Foresight** — система раннего предупреждения о сбоях графика городского транспорта за 10–15 минут.
- Слоган: «Foresight — видит сбой графика за 15 минут до того, как он случится».
- В коде и инфраструктуре: compose-проект `foresight`, образы `foresight-<сервис>`; имя Python-проекта `foresight`.
  Внутренние пакеты (`shared`, `ml`, `backend`, `replayer`) не переименовываем.
- В интерфейсе — по-русски: «Форсайт · Диспетчер» (дашборд), «Форсайт · Администрирование» (админка).

## 2. Принципы

1. **Один код признаков для офлайна и онлайна** (`shared/features`). Модель на потоке видит ровно то же, что при обучении.
2. **Честность данных.** На момент `T` используется только телеметрия с `event_time ≤ T`, проходы детектора с
   `confirmed_at ≤ T`, плановое расписание и `cur_dev_s`. Факты `time_fact_begin`, `manual_fill` и разметку других точек
   **никогда** не используем как признаки. Синтетические копии ТС рядом по времени с точками test/validate из обучения исключены.
3. **Факт прохождения остановок восстанавливаем из GPS.** В validate и на потоке факта нет, поэтому детектор прохождения —
   ядро и признаков, и онлайн-проверки горизонта.
4. **Отказоустойчивость по умолчанию:** любой внешний сбой (эмулятор, ML, Redis, PostgreSQL) ведёт к деградации с
   индикацией на дашборде, а не к падению.
5. **Обучение, тесты и замеры — на сервере** с Docker и GPU (RTX 3060); стек для проверки поднимается на любой машине с Docker (CPU).

## 3. Компоненты

```
 emulator ─┐   NDTP/TCP                 XADD telemetry            XREADGROUP
 replayer ─┴──────────► ingest ─────────────────────► Redis ─────────────────► predictor (N реплик)
                          │  HSET vehicle:{id}      Streams + Hash + PubSub        │  признаки, окно (t+10, t+15]
                          │                              ▲                         │  POST /predict (batch)
                          │                              │ PUBLISH alerts          ▼
                          │                              └──────────────── ml-service (CatBoost + GRU ONNX, GPU)
                          ▼
                     PostgreSQL ◄── api (FastAPI: REST + WebSocket + Swagger) ◄── dashboard + admin (nginx)
               (прогнозы, алерты,         ▲ SUBSCRIBE alerts, чтение состояния из Redis
                факты, версии моделей)
                                   Prometheus ◄── /metrics всех сервисов ──► Grafana
```

| Сервис | Стек | Ответственность |
|---|---|---|
| `emulator` | официальный образ `ndtp-telemetry-emulator:1.0` (API 18080) | живой NDTP; доказывает совместимость с эталоном. Настраивается автоматически init-контейнером `emulator-init` |
| `replayer` | Python 3.12, asyncio | **настоящий NDTP** из исторического `traffic.csv` с исходными метками времени и ускорением x1…x60; `unitId = unit_id`. Основной источник демо. Режим `emulator-bridge` гонит те же треки через официальный эмулятор (`fields`) |
| `ingest` | Python 3.12, asyncio | NDTP-сервер :9201 (кодек `shared/ndtp.py`, анти-DoS бюджет CRC), маппинг `unitId → tr_id`, запись в Redis Stream `telemetry` и горячего состояния `vehicle:{id}` (TTL). Масштабируется по `unitId` |
| `predictor` | Python 3.12, asyncio | consumer group на `telemetry`: детектор прохождения остановок на потоке, признаки (`shared/features`), тик прогнозов по часам потока, окно `(t+10, t+15]`, batch в `ml-service`, алерты, онлайн-сверка с фактом, запись в PostgreSQL, `PUBLISH alerts`. N реплик, ТС шардируются по consumer group |
| `ml-service` | Python 3.12, FastAPI, CatBoost, ONNX Runtime GPU | stateless: `POST /predict` (прогноз, P10/P50/P90, `p_late`, вклад признаков), `GET /model/info`, `POST /model/reload`, `/health`, `/metrics`. Обучение — CLI `ml train` в том же образе, версии моделей регистрируются в PostgreSQL |
| `api` | Python 3.12, FastAPI | REST + WebSocket для дашборда и админки, Swagger «Foresight · API», чтение состояния из Redis и журнала из PostgreSQL, `SUBSCRIBE alerts` → WS, управление replayer/эмулятором, What-if |
| `redis` | Redis 8 (AOF) | шина событий (Streams), горячее состояние ТС (Hash + TTL), pub/sub алертов |
| `postgres` | PostgreSQL 18 | журнал прогнозов и алертов, восстановленные факты (онлайн-разметка для дообучения), метрики, версии моделей, настройки порогов |
| `prometheus`, `grafana` | Prometheus 3, Grafana 13 | сбор метрик всех сервисов, готовые дашборды производительности (provisioning из репо) |
| `dashboard` | React + Vite + TypeScript + MapLibre GL + Ant Design, nginx | экран диспетчера и админка `/admin` |

**Почему Redis Streams, а не Kafka:** та же модель (лог + consumer groups + ack), но один лёгкий контейнер. Kafka для
десятков–тысяч ТС избыточна; при росте до масштаба города интерфейс шины меняется на Kafka без изменения сервисов.

**Внешние контракты.**
- `replayer/emulator → ingest`: NDTP по TCP, порт 9201.
- `ingest → predictor`: Redis Stream `telemetry` (поля: `unit_id`, `tr_id`, `ts`, `lon`, `lat`, `speed`, `course`, `valid`, `doors`).
- `predictor → ml-service`: `POST /predict`, JSON batch, таймаут 500 мс, при ошибке — fallback.
- `predictor → api`: Redis pub/sub `alerts`, `predictions`; журнал в PostgreSQL.
- `api → dashboard`: REST (`/api/vehicles`, `/api/alerts`, `/api/incidents/{id}`, `/api/routes`, `/api/stringline`,
  `/api/metrics/horizon`, `/api/metrics/perf`, `/api/whatif`, `/api/replay/*`, `/api/admin/*`) и WebSocket `/ws`.
- Swagger: у `api` и `ml-service`.

## 4. ML-ядро (критерий 1)

**Постановка.** Для точки `(tr_id, T)` предсказать задержку на целевой остановке с плановым прибытием в `(T+10, T+15]`. Метрика — MAE.

**Детектор прохождения остановок (map matching)** — `shared/stops.py`, готов: последовательное сопоставление GPS с плановыми
остановками ТС (маршруты круговые), момент прохода по отрезку между точками, особые правила для конечных (прибытие/отправление),
`confirmed_at` — момент, когда проход достоверно известен онлайн; строго каузален.

**Признаки на момент `T`** — `shared/features.py`, готов (54 в модели v1): отклонение по детектору и его тренд, привязка GPS
к плану, движение и простои, маршрут до цели, отстой на конечной, «физика», час, lead.

**Модели.**
- v1 (готово): CatBoost `loss=MAE`, ансамбль 4 моделей; CV 77.0, test 75.8, score 0.87636.
- v2: CatBoost `MultiQuantile` (P10/P50/P90) → `p_late = P(delay > 120 c)` и ожидаемая ошибка; PyTorch GRU по последовательности
  телеметрии за 15–20 мин + табличные признаки → ONNX (+ INT8); ансамбль с весами по out-of-fold MAE.
- Причина задержки: правила по признакам + вклад признаков (CatBoost SHAP).

**Валидация.** GroupKFold по семьям ТС (реальное ТС + его синтетические копии); test — holdout. Честный ориентир качества
на потоке — CV (77–82 с), а не test. Финальная модель — на train + test. Лог — `docs/submissions.md`.

**Дообучение.** Детектор на потоке сам производит разметку (факт прохождения), predictor пишет её в PostgreSQL
(`stop_passages`, закрытые прогнозы). Полное обучение — `python -m ml.train` (v1, CatBoost) и `python -m ml.train_v2`
(v2, CatBoost + GRU на GPU) на датасете; версия упаковывается в реестр (`python -m ml.registry pack`) и подхватывается
`POST /model/reload` без остановки потока. На потоке — простое дообучение из админки («Переобучить на потоке»,
`ml/online.py`): поправка `a + b · прогноз` активной версии по её закрытым прогнозам (признаков в журнале нет) →
новая версия `<база>-online<N>`, если поправка снизила MAE на поздних 30 % прогнозов; включается кнопкой
«Активировать».

**Бюджет сабмитов:** лучший результат уже засчитан; сабмитим только явные улучшения по CV.

## 5. Поток и прогнозы (критерии 2–3)

- **Приём (ingest):** asyncio, соединение на устройство, потоковый декодер кадров, проверка CRC, бюджет ошибок на соединение
  (анти-DoS), разбор ячеек (Nav00, Irma04 — двери, остальные — пропуск по длине). Уже реализовано в `backend/` + `shared/ndtp.py`,
  переносится в сервис `ingest`.
- **Время.** Для replayer — время из пакета; эмулятор ставит текущее. Predictor работает по «часам потока» (максимальный
  правдоподобный `timestamp`); сброс часов при перезапуске replayer.
- **Тик прогнозов (predictor):** каждые 30 с потокового времени. Для каждого активного ТС — все остановки с планом в
  `(t+10, t+15]`: признаки → batch в `ml-service` → прогноз. Алерт, если `p_late` или `pred_delay_s` выше порога; алерт хранит
  `issued_at`, остановку, план, прогноз, интервал, вероятность, причину, участок.
- **Онлайн-сверка:** когда детектор подтверждает проход целевой остановки, прогноз закрывается фактом: ошибка, lead time,
  флаг «выдан заранее». Отсюда онлайн-MAE и распределение горизонта.
- **Расписание:** загружается при старте (`schedule_plan.csv` или `schedule.csv` без факта).
- **Сбивка ТС (bus bunching):** predictor по прогнозам прибытия ТС одного маршрута на общие остановки выявляет пары с
  интервалом меньше порога — отдельный тип инцидента.

## 6. Горизонт и честность прогноза (критерий 2)

- Прогноз создаётся только для остановок с планом строго в `(t+10, t+15]` потокового времени.
- Страница дашборда **«Честность прогноза»**: гистограмма заблаговременности (все алерты в 10–15 мин), счётчик
  «алертов задним числом» (0), онлайн-MAE по закрытым прогнозам в реальном времени против baseline `cur_dev_s`,
  доля опозданий, предупреждённых заранее.
- `make demo` запускает replayer x30 — за 2–3 минуты на странице видны закрытые прогнозы и статистика горизонта.

## 7. Дашборд (критерий 4)

Правило «понятно за 5 секунд»: сверху KPI (ТС в риске, средний прогноз опоздания, алерты за 15 мин, состояние системы),
слева карта, справа список проблемных ТС по убыванию риска. Светлая тема: белые поверхности, светло-голубой акцент (решение пользователя 27.09).
- **Карта** MapLibre: линии маршрутов (по остановкам расписания), ТС с цветом риска (зелёный < 60 c или `p_late` < 0.3,
  жёлтый — промежуточно, красный > 120 c или `p_late` > 0.6) и курсом, подсветка проблемных участков.
- **Карточка инцидента:** ТС и маршрут, целевая остановка, план, прогноз с интервалом P10–P90, вероятность, причина
  (человекочитаемая), участок на карте, рекомендация диспетчеру, время выдачи и время до события.
- **График движения** (бывш. «нитка»; диаграмма «время × остановки маршрута»): плановые нитки, фактические (по детектору) и
  прогнозные продолжения на 15 мин вперёд; видно накопление опоздания и сбивку ТС. Родной инструмент диспетчера.
- **Сбивка ТС:** инциденты «два ТС идут вплотную / разрыв интервала» с рекомендацией (придержать ТС, выпуск резерва).
- **What-if (обязательно):** выбрать маршрут и момент → «выпустить резервное ТС» или «придержать ТС на конечной на N мин» →
  пересчёт интервалов и ожидаемых задержек на ближайший час, сравнение «до / после».
- **Страницы:** «Оперативная обстановка», «График движения», «Честность прогноза», «What-if», «Производительность» (ключевые метрики +
  ссылка на Grafana).
- Обновление по WebSocket, индикаторы «нет связи», «данные устарели», «деградация» (ML/Redis/PostgreSQL).
- Подложка — растровые OSM-тайлы с атрибуцией; без интернета карта работает без подложки (маршруты и ТС видны).

**Причины (правила + вклад признаков):** длительный простой на остановке, низкая скорость на участке, плановый отстой на конечной,
накопленное опоздание, сбивка с соседним ТС, потеря GPS. Для каждой — рекомендация: выпуск резерва, корректировка отправления с
конечной, связь с водителем, проверка участка.

## 7a. Админка (27.09)

- Раздел `/admin` того же фронтенда, UI — **Ant Design** (`antd` 6.6, `@ant-design/icons` 6.3; пакеты в npm-кэше сервера).
- Работает поверх `api` (`/api/admin/*`, в Swagger).
- Состав:
  - источник потока: старт/стоп/скорость replayer, эмулятор, статус соединений ingest;
  - пороги риска и алерта (хранятся в PostgreSQL, применяются predictor на лету);
  - модели: активная версия, CV/test/онлайн-MAE по версиям, переобучение и переключение версии, fallback;
  - журнал алертов и прогнозов с фильтрами и экспортом CSV;
  - справочники: ТС (`unitId ↔ tr_id`), маршруты, остановки;
  - здоровье сервисов (Redis, PostgreSQL, ml-service, ingest, predictor).

## 8. Производительность и надёжность (критерий 5)

- `/metrics` во всех сервисах: latency инференса (p50/p95/p99), время тика, лаг consumer group, пакеты/с, битые кадры,
  переподключения, состояние зависимостей. **Grafana** с готовыми дашбордами (provisioning из репо).
- Цели: инференс batch всех активных ТС < 100 мс, end-to-end «пакет → дашборд» < 1 с, лаг очереди ≈ 0.
- Нагрузочный прогон: replayer x60 по всем ТС + синтетическое размножение ТС (x10); отчёт в `docs/performance.md`.
- Деградация (каждая проверяется **chaos-сценарием** `scripts/chaos.sh` и показывается на демо):
  - обрыв NDTP — ТС «нет связи», после реконнекта состояние продолжается;
  - `ml-service` недоступен — fallback-прогноз в predictor (последнее GPS-отклонение с коэффициентом из обучения), флаг `degraded`;
  - Redis недоступен — ingest и predictor переходят на внутреннюю очередь процесса, api отдаёт последнее известное состояние;
  - PostgreSQL недоступен — запись в журнал буферизуется в памяти и дописывается после восстановления;
  - потока нет — последнее известное состояние и прогноз по истории с индикатором «устарело».
- Холодный старт: модель в образе `ml-service`, healthchecks и `depends_on: condition: service_healthy`; время старта
  замеряется и пишется в `docs/performance.md`.
- Запуск одной командой: `make demo` (compose + init эмулятора + replayer x30 + открыть дашборд).

```
shared/       # общий пакет: NDTP-кодек, загрузка данных, детектор остановок, признаки, клиенты Redis/PostgreSQL

scripts/      # сабмит, нагрузка, chaos, утилиты
dataset/      # исходные данные (в git)
docker-compose.yml, Makefile
```
