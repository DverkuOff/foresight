# Форсайт (Foresight) · инструкция для жюри

Форсайт за 10–15 минут до планового прибытия прогнозирует задержку транспорта по потоковой телеметрии NDTP,
объясняет причину, поднимает алерты и показывает всё диспетчеру на дашборде. Каждый прогноз затем сверяется с
фактом прохождения остановки прямо на потоке.

Ниже — как запустить систему за несколько минут, как подать поток и где проверить каждый критерий.

## 1. Запуск

Нужны Docker Engine ≥ 25 с Docker Compose ≥ 2.21, `make`, `curl`, ~6 ГБ свободной памяти и свободные порты
8000–8003, 8010, 8080, 3000, 9090, 9201, 18080. Python на хосте не нужен.

```bash
git clone https://github.com/DverkuOff/foresight.git
cd foresight
make dataset    # датасет организаторов по ссылке из ТЗ (Яндекс.Диск, 147 МБ) с проверкой sha256
make demo       # сборка образов, запуск 13 сервисов, поток test-дня ×30 с 06:00 по кругу
```

`make demo` ждёт, пока все сервисы станут healthy, и печатает адреса. Первая сборка образов — несколько минут
(скачиваются базовые образы и зависимости), повторный запуск — секунды. Минута реального времени — 30 минут
потока; первые прогнозы и инциденты появляются в течение минуты после старта.

Без `make`: `cp .env.example .env` (задать пароль администратора Grafana), `REPLAY_AUTOSTART=1 docker compose up -d
--build --wait`.

Остановить: `make down` (данные сохраняются), `make clean` (с удалением данных).

## 2. Где смотреть

| Что | Адрес | Что там |
|---|---|---|
| **Дашборд диспетчера** | http://localhost:8080 | карта ТС с риском, проблемные ТС, карточка инцидента, график движения, честность прогноза, What-if, производительность, администрирование |
| Swagger API | http://localhost:8000/docs | REST и WebSocket дашборда: ТС, инциденты, алерты, прогнозы, метрики, What-if, админка |
| Swagger ML | http://localhost:8003/docs | `POST /predict` — прогноз, P10–P90, вероятность опоздания, вклад признаков |
| Grafana | http://localhost:3000/grafana/ | 5 дашбордов: обзор системы, поток, модель, надёжность, инфраструктура (просмотр без входа) |
| Prometheus | http://localhost:9090 | метрики всех сервисов и 25 правил алертов |
| Управление потоком | http://localhost:8010/docs | replayer: старт, стоп, скорость |
| Документация | [GitHub Pages](https://dverkuoff.github.io/foresight/) | эта инструкция, архитектура, отчёт ML, справочник по коду, OpenAPI всех сервисов |

Внизу меню дашборда — ссылки на Swagger API, Grafana и документацию; Swagger и Grafana открываются и через порт
дашборда (http://localhost:8080/docs, http://localhost:8080/grafana/). `make status` — краткая сводка: здоровье
сервисов, часы потока, лаг очереди, ТС, прогнозы.

Страницы дашборда (меню слева): «Оперативная обстановка» (карта и проблемные ТС), «График движения», «Честность
прогноза», «What-if», «Производительность», «Администрирование». В «Администрировании» вкладки: **Поток** (источник,
скорость, начало дня, состояние приёма NDTP), **Пороги** (границы зелёного / красного и уровень алерта — применяются
на лету), **Модели** (версии с метриками, «Активировать», «Переобучить на потоке»), **Журнал** (алерты и прогнозы с
фильтрами, экспорт CSV), **Здоровье** (сервисы и зависимости), **Справочники** (ТС, маршруты, остановки).

## 3. Как подать поток

1. **Исторический датасет (по умолчанию).** Replayer проигрывает `dataset/<split>/traffic.csv` как настоящие
   NDTP-соединения — по одному TCP-соединению на ТС, с исходными интервалами между пакетами, ускоренно.
   - на дашборде: «Администрирование» → «Поток» — начало дня, скорость ×1…×60, «Запустить заново», «Сменить
     скорость», «Остановить»;
   - из консоли: `make replay-start REPLAY_SPEED=60 REPLAY_START=07:00`, `make replay-stop`;
   - через API: `POST /api/replay/start` с `{"split": "test", "speed": 30, "start": "06:00", "loop": true}`.
2. **Эмулятор NDTP организаторов.** Контейнер эмулятора входит в стек (образ `make` загружает из
   `dataset/ndtp-telemetry-emulator.tar`). Два способа:
   - исторический день через эмулятор: «Администрирование» → «Поток» → источник «через эмулятор» → «Запустить
     заново» (или `make replay-start REPLAY_MODE=bridge`) — replayer передаёт позиции ТС в эмулятор, а тот шлёт NDTP
     в приёмник;
   - живой поток с прогнозами, как на проверке (текущее время в пакетах, реальный темп):
     `make replay-start REPLAY_MODE=bridge REPLAY_SPEED=1 REPLAY_START=$(TZ=Europe/Moscow date +%H:%M)` — replayer
     ведёт ТС дня test по их трекам через эмулятор с текущего московского времени суток, эмулятор ставит текущее
     время, первые прогнозы — через несколько минут;
   - собственный поток эмулятора: `make emulator` останавливает replayer и направляет поток эмулятора в приёмник
     (`EMU_UNITS=664030,794446` — выбор ТС; координаты задаёт сам эмулятор, поэтому это проверка приёма и разбора
     NDTP, а не прогнозов). Вернуть исторический поток — `make demo` или `make replay-start`.
3. **Любой источник NDTP.** Приёмник слушает `tcp://<хост>:9201`; ТС сопоставляются с расписанием по
   `unitId → tr_id` из датасета.

**Время живого потока.** Расписание — один день датасета (06.01.2026, московское время). Исторический поток несёт
время этого дня, а живой (эмулятор, реальные трекеры) — текущее время UTC: приёмник переносит его на день
расписания по московскому времени суток (`FORESIGHT_REALTIME_PLAN_DAY`, `FORESIGHT_REALTIME_TZ_OFFSET_S`), так ТС
встречают свои плановые остановки и прогнозы идут как на истории. На дашборде часы потока показывают 06 января.

Источник один за раз: у приёмника одни часы потока. При смене источника часы переходят на новую шкалу
автоматически, прогнозы старой шкалы закрываются как «сброс».

## 4. Проверка по критериям

### Точность прогноза (MAE)
- Сабмит на платформе: **score 0.87636** (модель v1, MAE на test 75.8 с при baseline `cur_dev_s` 93.4 с).
- Воспроизвести файл сабмита: `make submission` — прогноз по validate в образе ml-service за ~10 с, результат
  `artifacts/submission.csv` побайтно совпадает с загруженным (`BUNDLE=v2` — ансамбль CatBoost + GRU).
- Отчёт: [ML-отчёт](ml-report.md) — признаки, модели, кросс-валидация по ТС, интервалы, калибровка.
- Модель честная: признаки только из телеметрии до момента прогноза, без факта validate.

### Горизонт 10–15 минут
- Дашборд → «Честность прогноза»: каждый прогноз выдан для остановки с планом через 10–15 минут (100% в окне),
  **алертов и прогнозов задним числом — 0**, онлайн-MAE против baseline по часам, доля опозданий,
  предупреждённых заранее, заблаговременность до планового и до фактического прохода.
- API: `GET /api/metrics/horizon`, журнал прогнозов со сверкой — `GET /api/predictions?status=closed`.
- Подробно: [онлайн-проверка](online-validation.md) — поток test-дня даёт те же прогнозы, что офлайн.

### Система из трёх модулей в Docker
- **ML-ядро** — `ml-service` (CatBoost + ONNX Runtime на CPU, реестр версий `models/`). Обучение — `make train`: тот же
  образ, ~1 мин на CPU, test MAE 75.8 с — как у модели сабмита (ансамбль v2 с GRU обучается на GPU: `ml/train_v2.py`);
  дообучение на потоке — «Администрирование» → «Модели» → «Переобучить на потоке».
- **Backend** — `ingest` (приём и разбор NDTP, сопоставление с расписанием), `predictor` (детектор остановок,
  признаки: текущее отклонение, скорость на сегменте, время простоя; тик прогнозов каждые 30 с потока, алерты),
  `api` (REST + WebSocket + Swagger); Redis Streams — шина, PostgreSQL — журнал.
- **BI-дашборд** — `dashboard` (React + MapLibre + Ant Design, nginx).
- Запуск одной командой (`make demo`), healthcheck у всех сервисов, `docker compose ps` — 13 сервисов.

### BI-дашборд
- Карта: ТС с цветом риска (зелёный / жёлтый / красный), стрелка курса, линии маршрутов по дорогам (GPS-треки, привязанные к улицам),
  пульсация у красных, подсветка участка инцидента.
- Карточка инцидента (клик по ТС в списке «Проблемные ТС»): прогноз опоздания с интервалом P10–P90, вероятность,
  причина и вклад факторов, участок, рекомендация, отклонение за 30 минут и прогноз на 15 минут.
- Обновление в реальном времени через WebSocket (ТС, инциденты, алерты, часы потока).
- График движения (время × остановки: план, факт, прогноз с P10–P90 от позиции ТС), What-if (резерв / придержка ТС),
  производительность со встроенными панелями Grafana, администрирование (поток, пороги, модели и переобучение на
  потоке, журнал с CSV, здоровье сервисов, справочники).

### Производительность и надёжность
- Дашборд → «Производительность»: p95 «пакет → обработка» ~0,05–0,1 с, инференс p95 < 100 мс, тик прогнозов
  (все ТС) p95 < 0,3 с, лаг очереди 0. Подробно: [производительность](performance.md).
- Отказы: `make chaos` по очереди останавливает приёмник, Redis, PostgreSQL, ML-сервис, replayer и печатает
  `ok / FAIL` и время восстановления (~4 мин, проверено на чистом клоне: все проверки проходят); вручную — `docker compose stop redis; sleep 30; docker compose start redis`. Сервисы не падают,
  отдают последнее состояние с пометкой `degraded`, буферизуют и дописывают данные после восстановления.
  Без ml-service прогнозы продолжаются по резервной формуле.

## 5. Дополнительные возможности

- Ансамбль CatBoost + PyTorch GRU по последовательности телеметрии (ONNX, квантование INT8), интервалы P10–P90
  (конформная калибровка), вероятность опоздания, вклад признаков (SHAP) → причина для диспетчера.
- Map matching: детектор проходов остановок по GPS; линии маршрутов — GPS-треки целых направлений, привязанные к
  дорогам (OSRM match), без заездов к остановкам; где автобусу можно больше, чем легковой (выделенные полосы), — сам
  трек.
- What-if: выпуск резервного ТС и придержка ТС — интервалы, ожидание пассажиров, опоздания, сбивки «до / после».
- Алерты уровня инцидента с гистерезисом и эскалацией, детектор сбивок (bunching).
- Онлайн-сверка каждого прогноза с фактом, онлайн-MAE против baseline.
- Дообучение на потоке: «Администрирование» → «Модели» → «Переобучить на потоке» подбирает поправку прогноза активной
  версии по её закрытым прогнозам и сохраняет новую версию в реестр (включается кнопкой «Активировать», без
  остановки сервиса).
- Observability: Prometheus, 25 правил алертов, 5 дашбордов Grafana; администрирование на Ant Design.

## 6. Если что-то пошло не так

- Порт занят: `make demo DASHBOARD_PORT=8081 API_PORT=18000` (любой порт — через переменные `*_PORT`, см. `make help`).
- Старый Docker: `make up` проверяет версии и подсказывает; `DOCKER_CHECK=0` — пропустить проверку.
- Нет интернета: карта работает без подложки (маршруты и ТС видны), остальное — полностью офлайн.
- `make status` показывает, какой сервис лежит, и команду, чтобы его поднять; `make logs SERVICES=predictor`.
