# Foresight · производительность и надёжность

Все замеры — на одном сервере (10 CPU, 20 ГБ RAM, Docker 29.2), весь стек в Docker Compose, модель на CPU,
27.09.2026. Цифры на странице «Производительность» дашборда и в `GET /api/metrics/perf` считаются так же: p95 за
последние 5 минут по собственным метрикам сервисов (гистограммы Prometheus).

## 1. Итог

| Требование ТЗ | Результат |
|---|---|
| Задержка обработки < 1–2 с на ТС | пакет NDTP → обработка в predictor: **p95 0,05–0,24 с** при любой проверенной нагрузке |
| Работа без очередей | лаг consumer group Redis Streams в среднем **0–10 записей** и сразу рассасывается; при ×120 ни один тик не пропущен |
| Прогноз по всем ТС | тик прогнозов (детектор + признаки + модель для всех ТС) **p95 ≈ 0,25 с** раз в 30 с потокового времени |
| Инференс | `POST /predict` (пакет ТС, CatBoost + ONNX на CPU): **p95 75 мс**, при ×120 — до 180 мс |
| Пропускная способность приёма | **~2000 пакетов/с** на одном приёмнике при 39 % одного ядра ≈ 24 000 ТС с пакетом раз в 12 с |
| Не падает при обрыве связи | отказ приёмника, Redis, PostgreSQL, ML-сервиса, источника — без падений, с буферизацией и восстановлением (§4) |

## 2. Конвейер и где измеряется

```
NDTP (TCP 9201) → ingest: разбор, CRC, unitId→tr_id → Redis Stream foresight:telemetry
   → predictor (consumer group): окно трека, детектор проходов, признаки, раз в 30 с потока — тик прогнозов
      → ml-service POST /predict (пакет всех ТС) → алерты, инциденты → Redis (горячее состояние, pub/sub), PostgreSQL
         → api (REST + WebSocket) → дашборд
```

| Метрика | Откуда |
|---|---|
| пакет → обработка | `foresight_predictor_event_latency_seconds` — от приёма пакета ingest до обработки predictor |
| тик прогнозов | `foresight_predictor_tick_seconds` — весь тик: детектор, признаки, запрос к модели, алерты |
| инференс | `foresight_ml_request_duration_seconds{endpoint="/predict"}` — весь батч в ml-service |
| лаг | `foresight_consumer_lag` — записи потока, ещё не выданные predictor |
| поток | `packets_per_s` статистики ingest (окно 10 с) |

### C. Пропускная способность приёма: синтетический NDTP (`scripts/loadtest.py`)

Виртуальные устройства, каждое на своём TCP-соединении, шлют навигационные пакеты с заданным интервалом
(путь «NDTP → разбор → Redis Stream → consumer group»).

| Нагрузка | Принято, пакетов/с | пакет → обработка p95 | Лаг | CPU ingest | Ошибки |
|---|---|---|---|---|---|
| 500 устройств × 1 пакет/с | 490–500 | 0,15–0,20 с | 0–9 | 13 % | 0 |
| 1000 устройств × 2 пакета/с | 1800–1990 | 0,025–0,05 с | 10–41 | 39 % | 0 соединений, 0 CRC, 0 разбора |

Одновременно принимается до 1024 соединений (защита NDTP-порта от перегрузки, `FORESIGHT_NDTP_MAX_CONNECTIONS`);
лишние закрываются сразу, приёмник продолжает работать. Воспроизвести (стек поднят, replayer остановлен —
`make replay-stop`; устройства синтетические, прогнозов по ним нет):

```bash
docker run --rm --network foresight_default -v "$PWD:/src" -w /src -e PYTHONPATH=/src \
  foresight-replayer:latest python scripts/loadtest.py --host ingest --devices 1000 --interval 0.5 --duration 60
```

## 4. Надёжность

Проверяется `make chaos` (по очереди роняет и поднимает сервисы, печатает `ok / FAIL` и время восстановления)
и вручную `docker compose stop <сервис>`.

| Отказ | Поведение | Восстановление |
|---|---|---|
| обрыв NDTP-приёма (ingest) | api через ~10 с помечает ТС `offline`, ответы и WebSocket — `degraded: true`; replayer копит пакеты | ingest healthy через 3–4 с, 30 ТС переподключаются за ≤ 5 с, очередь досылается, сбросов часов 0 |
| Redis | ingest копит события в памяти, api отдаёт последнее состояние (`degraded`) | буфер дописывается, лаг → 0, потерь нет; `/health` снова `ok` через 5–7 с |
| PostgreSQL | журнал копится в памяти писателя | дописывается после подъёма, потерь нет |
| ml-service | predictor сразу переходит на резервную формулу (`forecast_source: fallback`), тики не прерываются | прогнозы снова от модели через 4–5 с после start |
| источник (replayer) / смена источника | часы потока переходят на новую шкалу, прогнозы старой закрываются как «сброс» | демо продолжается само через 3 с |
| вся машина (`docker compose restart`) | — | стек снова работает через ~7 с |

Все `/health` в это время отвечают 200 со `status: degraded` и списком упавших зависимостей; Prometheus поднимает
алерты (25 правил), страница «Производительность» показывает состояние каждого сервиса.

## 5. Почему это быстро

- приём на asyncio с потоковым разбором NDTP и пакетной записью в Redis Stream (pipeline);
- predictor держит окна треков в памяти, признаки считаются векторно, модель вызывается одним батчем на тик;
- модель на CPU: CatBoost (нативно) и GRU в ONNX Runtime с INT8-квантованием весов, без PyTorch в образе;
- api держит горячее состояние в памяти (синхронизация через pub/sub), WebSocket шлёт только изменения;
- запись в PostgreSQL — буферизованная, пакетами, вне горячего пути.
