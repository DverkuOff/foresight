# Foresight · проверка «поток = офлайн»

> Проверено 26.09.2026 на сервере (10 CPU). Скрипт — [`scripts/validate_online.py`](../scripts/validate_online.py),
> результаты прогонов — `artifacts/online/<прогон>/` (вне git). Критерий 2 ТЗ: прогноз формируется в окне
> T+10…15 мин до события, нет прогнозов задним числом, горизонт соблюдается на потоке.

## 1. Что и как проверяем

Два способа прогнать день **test** через тот же код, что работает в стеке:

- **simulate** — движок predictor (`backend.forecast.ForecastEngine` под `backend.predictor.PredictorCore`) в одном
  процессе: телеметрия `test/traffic.csv` в порядке `receive_time` (как её отдаёт replayer: точность NDTP, целые
  секунды), часы потока, окна треков, тик каждые 30 с, детектор на потоке, признаки, прогнозы, алерты, инциденты.
  Модель — версия реестра в процессе вместо HTTP; результат — таблицы, которые predictor пишет в PostgreSQL;
- **stack** — весь стек в Docker (redis, postgres, ingest, predictor, ml-service, api, replayer) с replayer **x60** по
  дню test с 05:00, затем `export` таблиц из PostgreSQL и статистики сервисов.

`evaluate` сопоставляет онлайн-прогнозы с `labels_test`: точка разметки `(tr_id, T, target_stop_id)` совпадает с
прогнозом, выданным на тике `T` для той же целевой остановки (тики идут по 30 с, `T` в разметке тоже кратны 30 с),
то есть lead ∈ [10, 15] мин. На тех же точках считаются та же модель офлайн (признаки `ml.dataset.build_split`) —
с `cur_dev_s` датасета и с его онлайн-аналогом — и baseline. Факты расписания и разметка используются **только** для
оценки, никогда — как вход движка (`backend/schedule.py` выбрасывает колонки факта при загрузке плана).

## 2. Две модели: для сабмита и для онлайн-оценки

| Версия | Обучена на | Для чего | test MAE офлайн |
|---|---|---|---|
| `v1` | train + test | сабмит validate (score 0.87636) | — (видела test) |
| `v2` | train + test | ансамбль CatBoost + GRU, P10–P90, `p_late`; модель сабмита v2 | — (видела test) |
| `v1-holdout` | только train | онлайн-оценка на дне test | 75.79 |
| `v2-holdout` | только train | онлайн-оценка на дне test; **по умолчанию в стеке** | 75.60 |

Стенд проигрывает день test, поэтому онлайн-MAE, посчитанная моделью, видевшей test, была бы утечкой (аудит F06).
`*-holdout` — тот же рецепт (те же признаки, гиперпараметры, веса ансамбля, калибровка `p_late` и поправка интервала
из OOF train), обученный только на train (`ml.dataset.leak_mask` убирает синтетические копии периодов test и
validate): `scripts/validate_online.py pack-holdout --bases v1,v2`. Их test MAE совпадает с train-only метриками
`docs/ml-report.md`. Версия в стеке — `FORESIGHT_MODEL_VERSION` (compose: `v2-holdout`).

## 3. Итог

Конфигурация стека по умолчанию: `v2-holdout`, онлайн-аналог `cur_dev_s` = медиана задержки трёх последних проходов,
подтверждённых детектором (`FORESIGHT_CUR_DEV_MODE=median3`), без последовательностей GRU (`FORESIGHT_ML_SEQUENCES=0`,
см. §6), алерты уровня инцидента.

| Что | Значение (день test) |
|---|---|
| прогнозов выдано / закрыто фактом детектора | 5015 / 4557 (simulate, весь день); 4339 / 3919 (стек x60, с 05:00) |
| lead «план − первая выдача» | все в (600, 900] с: 630…900 с (тики по 30 с) |
| прогнозов «задним числом» (выдан в момент прохода или позже) | **0** (simulate и стек) |
| алертов «задним числом» | **0** |
| lead «проход по детектору − первая выдача»: p5 / медиана / p95 | 746 / 943 / 1236 с; ≥ 10 мин — 99.3% |
| точек разметки с онлайн-прогнозом на тике `T` | 324 из 353 (91.8%) |
| онлайн-MAE на этих точках | **92.8 с** (стек: **92.3 с** на 279 из 308 точек окна 05:00–24:00) |
| та же модель офлайн на тех же точках, с онлайн-аналогом `cur_dev_s` | 92.3 с; \|онлайн − офлайн\|: медиана 1.3 с, p90 11.9 с |
| та же модель офлайн с `cur_dev_s` датасета | 78.8 с (все 353 точки — 75.8 с) |
| baseline «прогноз = `cur_dev_s` датасета» / «= онлайн-аналог» / ноль | 97.0 / 128.7 / 108.8 с |
| онлайн-MAE по факту детектора (все 4557 закрытых прогнозов) | 80.6 с (первая выдача — 90.1 с), baseline 127.3 с |
| интервал P10–P90: покрытие / средняя ширина | 79.0% (цель 80%) / 279 с |
| `p_late` (P(опоздание > 120 с)): Brier / климатология | 0.172 / 0.192 |
| доля fallback | 0% (ml-service доступен весь прогон) |

**Вывод «поток = офлайн».** При одинаковых входах поток и офлайн дают один прогноз: медиана расхождения 1.3 с, p90 —
12 с (остаток — точки, пришедшие в ingest позже `T` по `receive_time`: на потоке их ещё нет, офлайн-признаки берут
всё с `event_time ≤ T`). Разница между онлайн-MAE 92.8 и офлайн 75.8–78.8 — не расхождение кода, а подсказка
`cur_dev_s` датасета: это факт на последней остановке с **плановым** временем ≤ `T` (совпадает в 98.6% точек), и в
45% точек test этот факт наступает **после** `T` (ТС опаздывает) — информация из будущего, которой на потоке нет
(`scripts/validate_online.py analog`). На потоке она заменяется онлайн-аналогом по проходам детектора, и та же
модель офлайн с тем же аналогом даёт 92.3 с. При этом онлайн-модель лучше baseline с настоящей подсказкой
(92.8 против 97.0 с) и лучше нуля (108.8 с).

## 5. Онлайн-аналог `cur_dev_s`: медиана трёх проходов лучше NaN

CatBoost умеет пропуски, поэтому вариант «подсказки нет» (`NaN`) проверен наравне с аналогами. Итог по онлайн-MAE:
median3 **93.5** против NaN 102.2 (v1-holdout) и 97.2 против 103.1 (v2-holdout + GRU); с NaN разваливаются и алерты
(точность красных 23% против 55%). Аналоги (`validate_online.py analog`, MAE до `cur_dev_s` датасета / до цели на
test): последняя обычная остановка 71.2 / 125.5, медиана трёх 72.2 / **121.5**, последняя остановка 76.6 / 130.9,
последняя с задержкой подтверждения 60–300 с 84–112 / 132–145. Медиана трёх — лучшая по цели и по MAE модели на
потоке; она и выбрана (`FORESIGHT_CUR_DEV_MODE=median3`).

## 6. GRU v2 на потоке: реализован, по умолчанию выключен

Predictor строит последовательности телеметрии тем же кодом, что при обучении (`shared/sequences.py`, только точки
`≤ t` и проходы с `confirmed_at ≤ t`), по одной на ТС за тик, и шлёт их в `POST /predict` (расширение контракта §3:
`sequences` — base64 float32 по ключу, `sequence_id` у строки; без них ml-service считает CatBoost-часть). Замер на
потоке: с GRU онлайн-MAE 97.2 против 93.5 без него, по всем закрытым — 86.9 против 80.6; интервал P10–P90 покрывает
76.4% против 79.0%, Brier `p_late` 0.182 против 0.172. Причина — GRU v2 обучен как поправка к `cur_dev_s`
(`base: cur_dev_s` в манифесте) и на потоке получает онлайн-аналог вместо подсказки датасета, а у CatBoost-части
половина членов обходится без неё. Поэтому по умолчанию `FORESIGHT_ML_SEQUENCES=0`: `v2-holdout` отдаёт CatBoost-часть
(= ансамбль v1), P10–P90, `p_late` и ожидаемую ошибку; `FORESIGHT_ML_SEQUENCES=1` включает весь ансамбль. Чтобы GRU
помогал на потоке, его нужно переобучить с базой — онлайн-аналогом (или без базы).

## 7. Горизонт и покрытие

- Цели берутся только с плановым прибытием в `(t + 10 мин, t + 15 мин]` (lead «план − выдача» 630…900 с, ни одного
  вне окна); остановка, уже решённая детектором, целью не становится; поэтому прогнозов «задним числом» 0.
- Фактическая заблаговременность (проход − первая выдача) меньше 10 мин у 0.7% прогнозов: ТС пришло раньше плана
  больше чем на 5 мин (минимум 5.2 мин).
- 29 точек разметки из 353 без онлайн-прогноза на тике `T`: у 20 последняя точка GPS старше 15 мин (ТС неактивно:
  `FORESIGHT_ACTIVE_S`), у 10 ТС стоит ближе 150 м к целевой **обычной** остановке за 11 мин до плана — прогноз там
  мог бы прийти после прохода, поэтому он не выдаётся. Целевая **конечная отправления**, у которой ТС ждёт рейса,
  прогнозируется (проход — отправление, он впереди): это подняло покрытие с 89.0% до 91.8% при 0 «задним числом».

## 8. Алерты: на инцидент, а не на каждую остановку (аудит F07)

Раньше алерт выдавался на первый переход каждого прогноза «ТС × остановка» в жёлтый / красный — на один инцидент
приходилось ≈ 14 алертов. Теперь уровень ТС — риск ближайшей цели окна с гистерезисом 20 с, алерт — при открытии
инцидента и эскалации до красного, следующий — только после закрытия (4 тика в зелёном). Одна модель (v1 на train),
один день test:

| | До (алерт на прогноз) | После (алерт на инцидент) |
|---|---|---|
| алертов задержки | 2547 | **237** |
| инцидентов / алертов на инцидент | 183 / 13.9 | 168 / **1.41** |
| точность красных (факт расписания > 120 с на цели алерта) | 58.4% | 54.9% |
| точность жёлтых (факт ≥ 60 с) | 57.5% | 61.9% |
| полнота: опоздания > 120 с, у ТС которых был красный / хотя бы жёлтый уровень, пока остановка была в окне | 52.4% / 85.4% | 52.5% / 85.4% |
| алерт выдан ≥ 10 мин до прохода его остановки | 99.6% | 96.2% |
| алертов «задним числом» | 0 | 0 |

Число алертов упало в 10.7 раза при той же полноте; точность красных — в пределах шума (82 против 1176 проверенных,
и цель у алерта инцидента — ближайшая остановка в момент открытия, а не каждая). Проверены и соседние настройки:
подтверждение 2 тиками — полнота красных 47.3% (−5 п.п.) при той же точности; гистерезис 40 с — 180 алертов, но
точность красных 50%. Оставлены 1 тик, 20 с, 4 тика на закрытие. С v2-holdout (без GRU) цифры те же.

## 9. Детектор на потоке = офлайн

Инкрементальный детектор predictor против `shared.stops.detect_all` по всему дню (прогон sim_v2h_median3): то же
решение по 99.8% остановок, время прохода совпадает до 1 с у 98.7% (p99 — 2 с), подтверждение приходит через 40 с
(медиана) после прохода; расхождение с фактом расписания — медиана 1.3 с, p10…p90 −8.2…+4.0 с.

## 10. Fallback

Когда ml-service недоступен или не ответил за 500 мс, predictor прогнозирует сам: `14 + 0.23 · dev_1` (`dev_1` —
задержка на последней подтверждённой детектором остановке; при её отсутствии — онлайн `cur_dev_s`, иначе 14 с).
Коэффициенты — MAE-оптимум на train (реальные ТС, 1141 точка; `validate_online.py fallback-coef`): train 85.8 с,
test офлайн 98.3 с (ноль — 103.3, `cur_dev_s` датасета — 93.4). На потоке только fallback: 104.1 с против 92.8 у
модели; `source: fallback`, `degraded: true` в снимке, модель возвращается сама после пробы `/health`.

## 11. Производительность тика

Тик идёт раз в 30 с потокового времени: при x30 — раз в секунду, при x60 — раз в 0.5 с. Если тик не успевает, а
пачка событий уже дошла до следующей границы, граница пропускается (`foresight_predictor_ticks_lagging_total`),
очередь не копится.

| Прогон | Нагрузка | Тик: среднее / доля ≤ 100 мс / ≤ 250 мс / максимум | `POST /predict` | Пропуски |
|---|---|---|---|---|
| stack_final (x60, v2-holdout без GRU, SHAP-вклады) | 13 ТС расписания, до 11 активных, 18.5 целей на тик | 116 мс / 21% / 99.9% / < 0.5 с | среднее 64 мс, 98% ≤ 100 мс | `ticks_skipped` 10 (скачки часов потока, не отставание), `lagging` 0, лаг очереди 0, fallback 0 |
| stack_v2h (x60, v2-holdout + GRU) | то же | 179 мс / 2% / 86% / < 1 с | среднее 118 мс | `ticks_skipped` 10, `lagging` 0, fallback 0 |
| perf_train_v2h (simulate, train 06:00–10:00) | **25–36 активных ТС**, 68 целей на тик | p50 166 / p95 263 / p99 343 / max 432 мс (модель в процессе, без SHAP) | p50 36 мс | — |

Из чего складывается тик на 30+ ТС (p50): детектор 19 мс, признаки 103 мс, модель 36 мс. Тик укладывается в секунду
x30 с запасом в 3–4 раза; x60 на 13 ТС стенда проходит без единого пропуска; на 30+ ТС при x60 p99 тика 0.34 с (плюс
HTTP и SHAP ml-service, ~30 мс на пакет) — в 0.5 с укладывается, а редкий более долгий тик пропустит границу
(`lagging`), без очереди и без прогнозов задним числом.

## 12. Как воспроизвести

```bash
uv run python scripts/validate_online.py simulate --name sim_v2h_final --model v2-holdout   # весь день test
uv run python scripts/validate_online.py evaluate --name sim_v2h_final --model v2-holdout
uv run python scripts/validate_online.py alerts --names hold_median3,sim_v1h_median3        # алерты до / после
uv run python scripts/validate_online.py detector --name sim_v2h_median3                    # детектор
uv run python scripts/validate_online.py analog                                             # аналоги cur_dev_s
uv run python scripts/validate_online.py fallback-coef                                      # коэффициенты fallback
uv run python scripts/validate_online.py pack-holdout --bases v1,v2                          # holdout-версии
# стек: весь день test на x60, затем выгрузка из PostgreSQL
REPLAY_AUTOSTART=1 REPLAY_SPEED=60 REPLAY_START=05:00 REPLAY_UNTIL=00:00 REPLAY_LOOP=0 docker compose up -d --wait
uv run python scripts/validate_online.py export --name stack --project foresight
uv run python scripts/validate_online.py evaluate --name stack --model v2-holdout
```

Прогон «до» (алерт на каждый прогноз) — `hold_median3` от 26.09: код движка до перехода на алерты инцидента, та же
модель (ансамбль v1 на train, в процессе) и тот же `cur_dev_s` (median3).
